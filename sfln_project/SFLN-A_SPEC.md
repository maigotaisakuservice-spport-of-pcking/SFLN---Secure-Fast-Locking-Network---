# SFLN-A: Secure Data Encryption and Chunking Specification

## 1. Overview

This document defines the technical specification for SFLN-A, a protocol for securing data through advanced encryption and a unique chunking mechanism. The protocol is designed to be highly secure, resilient, and to align with the user's vision of "独自暗号" (custom crypto) and "データ分割" (data splitting).

## 2. Core Components

- **Master Key**: A single, high-entropy AES-256-GCM key used to encrypt an entire data payload. This provides both confidentiality and integrity.
- **Data Chunks**: The encrypted payload is split into fixed-size (1024-byte) segments for transmission.
- **Chunk Metadata**: Each chunk is prepended with a header containing information for reassembly, verification, and decryption.

## 3. Encryption & Splitting Process (Sender-side)

This process takes raw data and converts it into a set of SFLN-A chunks.

1.  **Input**: Raw data (e.g., a file, a message).

2.  **Step 1: Generate Master Key**: Generate a cryptographically secure 256-bit (32-byte) random key. This will be the **Master Key**.

3.  **Step 2: Encrypt Data**: Encrypt the entire raw data using **AES-256-GCM** with the generated Master Key. This operation produces two outputs:
    - `Encrypted Payload`: The encrypted data.
    - `Authentication Tag`: A tag generated by GCM used to verify data integrity upon decryption.

4.  **Step 3: Generate File ID**: Generate a unique `File ID` (e.g., a UUID) to identify all chunks belonging to the same original data.

5.  **Step 4: Split Encrypted Payload**: Divide the `Encrypted Payload` into chunks of **1024 bytes**. The final chunk may be smaller if the payload size is not a multiple of 1024.

6.  **Step 5: Select Key Chunk**: Randomly select a `Chunk Index` (from 0 to `Total Chunks - 1`). This is where the Master Key will be hidden.

7.  **Step 6: Construct Final Chunks**: For each chunk, construct a data packet with the following structure:
    - **Header**:
        - `File ID` (16 bytes): The UUID for the data.
        - `Total Chunks` (4 bytes): The total number of chunks.
        - `Chunk Index` (4 bytes): The sequence number of this chunk (0-based).
        - `Is Key Chunk` (1 byte): A boolean flag (1 if it's the key chunk, 0 otherwise).
        - `Payload Hash` (32 bytes): A SHA-256 hash of the `Chunk Payload` to ensure its integrity.
    - **Payload**:
        - The raw data segment from the `Encrypted Payload`.

8.  **Step 7: Embed Crypto Materials**:
    - For the randomly selected "Key Chunk", prepend its payload with three items: the 32-byte **Master Key**, the 16-byte **Nonce** (generated by AES-GCM), and the 16-byte **Authentication Tag**.
    - The `Payload Hash` for this specific chunk is calculated *after* these materials have been prepended.

## 4. Reassembly & Decryption Process (Receiver-side)

This process takes a set of SFLN-A chunks and restores the original data.

1.  **Input**: A collection of SFLN-A data chunks.

2.  **Step 1: Group and Verify Chunks**:
    - Group all received chunks by their `File ID`.
    - For each chunk, calculate the SHA-256 hash of its payload and verify it against the `Payload Hash` in its header. If any hash is invalid, abort the process as the data is corrupt.

3.  **Step 2: Identify Key Chunk and Sort**:
    - Find the single chunk with the `Is Key Chunk` flag set to 1.
    - Sort all chunks in ascending order based on their `Chunk Index`.

4.  **Step 3: Extract Crypto Materials**:
    - From the Key Chunk's payload, extract the first 32 bytes as the **Master Key**, the next 16 bytes as the **Nonce**, and the following 16 bytes as the **Authentication Tag**.
    - The remainder of the Key Chunk's payload is its segment of the encrypted data.

5.  **Step 4: Reassemble Encrypted Payload**:
    - Concatenate the payloads of all sorted chunks (using the trimmed payload from the Key Chunk) to reconstruct the original `Encrypted Payload`.

6.  **Step 5: Decrypt Data**:
    - Using the extracted **Master Key** and **Authentication Tag**, decrypt the reassembled `Encrypted Payload` with AES-256-GCM. The GCM mode will automatically fail if the tag is incorrect, providing a final integrity and authenticity check.

7.  **Output**: The original, decrypted raw data.

## 5. Design Rationale

- **"12,000-digit encryption"**: The user's request for extreme security is interpreted not as a literal key length, but as a need for a robust, modern, and highly secure cryptographic system. AES-256 is the industry standard for top-secret communication, and the GCM mode adds a critical layer of authentication. The "custom" nature of the protocol lies in the unique chunking, key-hiding, and metadata-wrapping strategy, not in creating a new, unaudited encryption algorithm (which would be a major security risk).
- **Security**: This protocol protects against eavesdropping (confidentiality), data tampering (integrity), and reordering or replay attacks (via chunk indexing and hashing). Hiding the key randomly within the data stream adds a layer of obscurity.
